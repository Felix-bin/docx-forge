# Project Positioning and Capability Boundary

[English](./project-positioning.md) | [Chinese](./zh/project-positioning.md)

---

This document defines docx-forge's long-term product position and the test for adding, retaining, or removing capabilities. It is a product policy, not a feature list or execution manual. This English file is canonical; the Chinese version is a synchronized translation updated in the same change.

## 1. Positioning

> **docx-forge is a chat-driven workflow that lets AI reason a document's argument into shape first, then write it and compile it into the user's own Word template as a real, natively styled, editable document — not pasted text with manual formatting. Its defining axis is template fidelity with native depth: every paragraph uses a template style, every number is generated by Word, and every reference is a live field.**

In form, docx-forge is a skill that runs inside an agent-capable AI tool. The workflow supplies document reasoning, contracts, and quality gates; deterministic tools handle conversion, compilation, validation, and preview; the chosen model still sets the quality ceiling.

The primary deliverable is a high-quality Word draft the user keeps refining, not a sealed final document.

## 2. Product Thesis

| Axis | Position | Consequence |
|---|---|---|
| Logic first | Settle reader, purpose, core conclusion, genre, and section skeleton before writing prose | Structure is reasoned, not inherited from source order |
| Template is the mold | The user's template owns styles, numbering, page setup, headers/footers, and fixed regions | The compiler never creates a style or writes direct formatting; a missing style is a template problem, not a page patch |
| Native depth | Headings are styles bound to multilevel lists; captions are `SEQ` fields; cross-references are `REF` fields; the table of contents is a `TOC` field; notes are real footnotes | The document survives editing in Word: renumbering, restyling, and field updates all work |
| Honest editability | The output is a draft; preview fidelity and pagination limits are stated, not hidden | Live preview is approximate; exact pagination comes from Word itself |
| User control | Templates, project state, and outputs stay local and inspectable | No hosted service, credits, or lock-in to one agent or model |

## 3. Target Users

People who must produce structured Word documents — reports, official documents, proposals, theses, SOPs — under an existing organizational template, who care that the result is correctly styled and editable, and who accept reviewing the direction and finishing the last mile in Word.

Not optimized for: zero-setup browser generation, free-form desktop publishing, or real-time co-editing.

## 4. Product Promises

| Promise | Meaning | Boundary |
|---|---|---|
| Template fidelity | Output uses only the selected template's styles, numbering, page setup, and fixed regions | A template defect is reported at ingestion, never silently patched with direct formatting |
| Logic before prose | Outline, evidence, and section obligations are planned before writing | A preservation request (fill or revise) keeps its source wording and order |
| Source fidelity | Facts and citations trace to sources or a bibliography | No invented references; unsupported claims are marked, not smoothed over |
| Engineering reliability | Explicit routes, a blocking checker, fingerprinted reports, recoverable project state | No silent fallbacks; a failed required gate stops export |
| Data stays local | Conversion, compilation, preview, and export run on the user's machine | The AI model and any chosen provider still receive the inputs they need |

## 5. Capability Model

| Domain | Responsibility |
|---|---|
| Document reasoning | Turn a topic or source bundle into a reader-aware purpose, genre, outline, and section plan |
| Template ingestion | Audit a user `.docx` / `.dotx`, report its defects, and distill a clean reusable template workspace |
| Native document authoring | Write DocMD sections and compile them into the template as native Word structure |
| Existing-document adaptation | Fill, revise, or annotate an existing document under a preservation contract |
| Review and delivery | Live preview, exact preview, annotation, validation, export, and read-back |

## 6. Non-goals

docx-forge is not intended to become:

- A general DOCX converter or arbitrary OOXML editor.
- A desktop-publishing or absolute-positioning layout tool.
- A template designer that invents an organization's format; it consumes and cleans templates the user supplies.
- A system that promises a perfect final document in one shot.
- An in-place upgrader of the user's original template files.

## 7. Capability Admission Test

Evaluate every proposed capability in this order:

1. **User job** — What real document task does it complete?
2. **Core contribution** — Does it deepen template fidelity or native structure, improve document reasoning, strengthen user control, or make delivery more reliable?
3. **Owned result** — What artifact, decision, or quality property does it create or protect?
4. **Invariant** — What must remain unchanged?
5. **Validation** — Can success and failure be checked without a vague claim?
6. **Evidence** — Is there a real repeated need or a demonstrated failure behind it?

Every new rule in a prompt file should trace to a demonstrated failure; a rule written in anticipation is a candidate for removal.
